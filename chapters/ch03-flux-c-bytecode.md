# Chapter 3 — FLUX-C Bytecode: How Constraints Execute

> **The Instruction Set That Can't Loop Forever**

---

## Why 43 Opcodes Is a Feature

x86_64 has approximately 3,000 instructions. ARM64 has about 1,200. FLUX-C has **43**.

This isn't a limitation. It's the entire point.

A Turing-complete instruction set can simulate any computation — including computation that never terminates. The classic example: `while (true) { }` compiles to valid machine code. The CPU runs it happily until the heat death of the universe.

FLUX-C cannot run forever. The 43 opcodes are chosen specifically to **exclude** the instructions that enable infinite loops:
- No arbitrary jumps (only forward jumps on conditions)
- No self-modifying code
- No recursion (call stack is finite and bounded at call time)
- No computed jumps (jump targets must be literals)

This is not a toy constraint. It's a **formal property**: every FLUX-C program terminates. Always. The Coq proof exists and is machine-checked.

## The 43 Opcodes, Grouped by Function

### Core (17 opcodes)
| Opcode | Args | Description |
|--------|------|-------------|
| LOAD | rd, addr | Load value from address |
| STORE | addr, rs | Store value to address |
| ADD | rd, rs1, rs2 | rd = rs1 + rs2 (bounded) |
| SUB | rd, rs1, rs2 | rd = rs1 - rs2 (bounded) |
| MUL | rd, rs1, rs2 | rd = rs1 × rs2 (overflow checked) |
| DIV | rd, rs1, rs2 | rd = rs1 / rs2 (zero-checked) |
| AND | rd, rs1, rs2 | rd = rs1 ∧ rs2 |
| OR | rd, rs1, rs2 | rd = rs1 ∨ rs2 |
| NOT | rd, rs | rd = ¬rs |
| XOR | rd, rs1, rs2 | rd = rs1 ⊕ rs2 (HDC operation) |
| CMP | rd, rs1, rs2 | rd = compare(rs1, rs2) |
| JMP | target | Unconditional forward jump |
| JZ | rs, target | Jump if rs == 0 |
| JNZ | rs, target | Jump if rs != 0 |
| CALL | addr | Call with bounded stack |
| RET | — | Return from CALL |
| HALT | — | Normal termination |

**Notice:** No `JMP` to arbitrary addresses — only forward jumps (no backward jumps = no loops). No `CALL` to arbitrary addresses — only bounded stack. This is not accidental.

## The Proof Chain: GUARD → FLUX-C → Coq → LLVM IR → Native

### Step 1: GUARD Constraint

```
GUARD battery_temp in [15, 55]
```

### Step 2: FLUX-C Bytecode

```asm
; battery_temp constraint: 15 <= temp <= 55
; Generated by GUARD compiler v3.0
; This bytecode is verifiable by Coq/FLUXC.v

section .data
lower_15:  .quad 15    ; 15°C lower bound
upper_55:  .quad 55    ; 55°C upper bound

section .text
check_battery_temp:
    ; Load temperature from input buffer
    movq    input_temp(%rip), %rax
    movq    %rax, temp_reg
    
    ; Check: temp >= 15
    cmpq    lower_15(%rip), %rax
    jl      violation      ; if temp < 15, FAIL
    
    ; Check: temp <= 55
    cmpq    upper_55(%rip), %rax
    jg      violation      ; if temp > 55, FAIL
    
    ; Both satisfied → return SATISFIED
    movq    $1, %rax        ; true
    ret
    
violation:
    ; Coq-verified safe shutdown sequence
    call    safe_shutdown   ; enters safe state
    movq    $0, %rax        ; false (dead code, but explicit)
    ret
```

### Step 3: Coq Verification

The same bytecode is verified by the Coq proof assistant:

```coq
Theorem fluxc_terminates:
  forall (c: constraint) (b: bindings),
    exists result, step_star c b result.

Theorem battery_temp_correct:
  forall (t: Z),
    sat (GUARD battery_temp in [15, 55]) t
    <-> (15 <= t <= 55)%Z.
```

`fluxc_terminates` proves the program always stops. `battery_temp_correct` proves the bytecode implements the constraint exactly.

### Step 4: LLVM IR → Native

The FLUX-C bytecode compiles to LLVM IR (.ll text format) for optimization:

```llvm
define i64 @check_battery_temp(i64 %temp) #0 {
entry:
  %cmp_low = icmp sge i64 %temp, 15
  %cmp_high = icmp sle i64 %temp, 55
  %both = and i1 %cmp_low, %cmp_high
  %result = select i1 %both, i64 1, i64 0
  ret i64 %result
}

; Compile with: llc -O3 -mcpu=skylake-avx512 constraint.ll
; Result: AVX-512 optimized native code
```

### Step 5: AVX-512 Execution

FM's benchmark: **35.9 GB/s** constraint checking throughput on Intel Xeon Phi (AVX-512, 512-bit vectors = 16 × i32 per instruction).

```c
// 16 constraints checked simultaneously via AVX-512
__m512i temps = _mm512_load_epi32(input_buffer);
__m512i lower = _mm512_set1_epi32(15);
__m512i upper = _mm512_set1_epi32(55);
__m512i pass = _mm512_and(
    _mm512_cmpge_epi32_mask(temps, lower),
    _mm512_cmple_epi32_mask(temps, upper)
);
// pass = all-ones if ALL 16 temperatures are valid
// 16 constraints per cycle → 410M constraints/sec
```

## Why No Loops Means No Performance Penalty

"Forward jumps only" sounds like it would limit what you can compute. In practice:

1. **All loops can be unrolled at compile time** if the iteration count is known. Most constraint iterations are over bounded structures (arrays, graphs) with fixed sizes.

2. **AVX-512 vectorization** replaces explicit loops with single instructions operating on 16 elements. The loop is implicit in the hardware.

3. **Batch constraint checking** is the common case. You have 10,000 constraints? Check them in 625 AVX-512 batches. One pass, no loops.

4. **Recursive algorithms don't need loops** if the recursion depth is bounded. FLUX-C's `CALL` is bounded at call time — you know the maximum stack depth before the program runs.

## Summary

FLUX-C's 43 opcodes are not a limitation — they're a formal constraint that guarantees termination.

The compilation pipeline:
1. GUARD constraint → FLUX-C bytecode (machine-verifiable)
2. FLUX-C → Coq proof (termination + correctness)
3. FLUX-C → LLVM IR → AVX-512 (35.9 GB/s)
4. FLUX-C → CUDA → GPU kernel (241M ops/sec)

No loops to verify. No arbitrary jumps to analyze. No undefined behavior to audit. Just 43 opcodes, a proof, and a constraint that either holds or fails.
